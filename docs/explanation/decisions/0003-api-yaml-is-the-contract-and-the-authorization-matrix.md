# ADR-0003 — `api.yaml` is the contract and the authorization matrix

- **Status:** Accepted
- **Date:** 2026-02-27

## Context

SIMVA has 155 documented operations and six roles. Both a role matrix and an API contract
existed in the design space, and the obvious implementations were:

- a roles file or an authorization module listing which role may call which path;
- OpenAPI tags describing *domains* (`studies`, `activities`, `users`), with a separate
  mechanism mapping domains to roles.

Either way there are two places to update when an endpoint is added, and they drift. The
project already had a history of that: the contract at SwaggerHub had been pinned at 1.0.0
since 2019 while `api.yaml` had moved to 2.0.0.

## Decision

Use the OpenAPI `tags` of an operation as the *set of roles allowed to call it*, and have the
auth middleware read `api.yaml` at startup.

```ts
// src/middlewares/auth.middleware.ts — Authenticator.initPaths()
const roleTag = methodConfig.tags[i].toLowerCase().slice(0, -1);
if (!roleTag.endsWith('_database') && !roleTag.endsWith('health')) {
  this.allowedRoutes[roleTag][method].push(path);
}
```

Untagged operations go into a `'*'` bucket every role inherits.

The tags are pluralised role names — `administrators`, `teachers`, `students`, `noroles`,
`lrsmanagers`, `garbagecollectors` — and the de-pluralisation is a single `slice(0, -1)`.

## Consequences

**Positive**

- **One file, three consumers:** the validator, the middleware, and the published
  documentation. They cannot disagree about which endpoints exist, because there is only one
  list.
- **The documented surface and the reachable surface are the same set.** For a project where
  documentation has historically lagged, this removes the usual failure.
- **Adding a role is a documentation-shaped change**, which is arguably the right shape for it:
  a reviewer reading "this operation is now available to service accounts" understands it.

**Negative**

- **A tag edit is an authorization change wearing a documentation costume.** There is no
  second file for a reviewer to cross-check, so review has to know the convention.
- **Role names must be singular and must not end in `s`.** `slice(0, -1)` is not a
  pluraliser. The `_database` and `health` escape hatches exist because some tags did not fit.
- **Diff volume.** Adding the `garbagecollector` role (`d5f9b14`, 2026-09-29) changed five
  lines of code and produced a 10,263-line `openapi.json` diff.
- **The published contract is still stale.** SwaggerHub has served 1.0.0 since 2019. The
  mechanism guarantees internal consistency, not external accuracy.
- **Planned-but-unimplemented endpoints are preserved in the contract.** 15 LTI operations and
  `/events`, `/tasklist`, `/uploads` are fully documented with schemas and have no handler. A
  client generated from the contract will be built against endpoints that answer 404.
- **`/activities/{id}/lrs/activities/status` is documented while the router serves `/state`**,
  so four LRS operations are unreachable by their documented path.

## Consequences of enabling response validation

Turning on `validateResponses: true` in the same week forced a multi-week rewrite of the
contract itself, because the schemas no longer described what the code produced:

- `a145b0c` — remove invalid `required` fields, standardise response references
- `6861cfd` — standardise operation ids and parameter names (+150/−226)
- `0914524` — add a thousand lines of error schemas (+1,123/−243)
- `55ebcea` — remove `current_user_id`, `current_user_username` and `current_user_permission`
  from response schemas, because per-caller injected fields cannot be a static contract

That last change is instructive about the limit of the idea: the contract can describe the
shape of a response, not its per-caller content.

## Keeping the drift visible

[`spec-vs-implementation.md`](../../reference/api/spec-vs-implementation.md) is regenerated by
`npm run update-docs`. It statically walks the router tree and reports three categories:
documented but not implemented, implemented but not documented, and path-parameter naming
differences. The convention cannot prevent drift; it can make it visible on every
documentation build.
